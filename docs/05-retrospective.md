# 复盘与仍待改进的问题

最难定位的是冲突组。首轮找到了两份候选制度，随后适配器只留下通用格式错误。增加脱敏采样后，完整重跑出现了另一条路径：模型读完两份文件却标为“部分已回答”，还建议按 15 天执行。两份条款都没有赋予 15 天优先级。将复现缩小到首次检索后的同一组候选，连续两次采样分别收到一个和两个读取动作。因此双调用可以解释一种失败路径，首轮丢失的响应无法还原。[完整定向复现](../examples/task04/diagnosis/conflict.json) · [调用数量采样](../examples/task04/diagnosis/decision2.json)

修改后，批量请求整批拒绝，每个调用 ID 都收到反馈，由模型在剩余步数内重新选一个动作。检索为空和发生真实工具错误分别判定。提示中明确了缺少用户条件与多个独立事项只答出一部分的区别。两个新增回归在旧实现上重现失败，修改后通过。第二轮冲突组改为读取双方并追问，早餐费组改为依据不足，住宿首轮仍然选错状态。[逐项对照](../examples/task04/live-second/review.md)

第二轮也暴露了新问题。超时后若换词检索成功但仍找不到制度，最后一次检索的成功标志会掩盖先前的超时。修改为分别记录本轮是否发生超时和最近检索的状态，新增回归覆盖该组合。该组合在本地回归通过。第三轮真实模型重试后成功命中，未触发重试后仍为空的路径。

第三轮为“部分已回答”增加两项用户原话的校验。用“只有一个住宿问题、缺目的地”和“已知城市、另问未覆盖的早餐费”作成对测试，检查模型选择的动作与终端状态，而不仅看答复里有没有询问城市。单问住宿首轮这次选择 ask_user，第二轮输入上海后引用 D02 正确作答。第三轮 5/6；每轮每组单次，不能据此估计稳定性。[最终评估与限制](../examples/task04/live-third/review.md)
